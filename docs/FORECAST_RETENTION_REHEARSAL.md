# Изолированная репетиция разделения прогнозов

28 октября 2026. Новый инструмент `scripts/rehearse_forecast_retention.py` работает
только с заранее сохранённым самостоятельным snapshot и pinned receipt проверки
retention. Создаёт две новые SQLite в отдельном каталоге; рабочую базу, сервисы,
модель и настройки торговли не переключает. Недописанный каталог остаётся для
разбора и не переиспользуется.

## Проверки

Инструмент повторно проверяет hash manifest, snapshot и preflight, условия времени,
схему и counts. Независимо пересчитывает ID обеих групп и сверяет их хеши с
preflight. При orphan outcomes, изменённых входах, неизвестной схеме, нехватке
места, превышении числа строк или срока — ошибка без receipt готового результата.
Размер источника, число строк, время, SQLite cache и reserve ограничены; при
создании новая директория и файлы не перезаписываются.

После копирования каждая SQLite проходит `integrity_check`. Отсортированное
объединение обеих частей сверяется с хешами исходных типизированных строк, включая
все версии outcome. Затем отдельный read-only audit повторяет это через SQLite
`UNION ALL` и перепроверяет file hashes. Это доказывает сохранность исходного
снимка в двух копиях, но не работу существующих читателей по обеим частям.

## Обязательные условия для реального перехода

- [x] Отдельная offline split/copy репетиция, counts, integrity, все typed rows и
  версии outcome; независимая SQL-сверка против pinned исходного snapshot.
- [x] Выявлена возможность будущего конфликта числовых outcome ID: в archive
  есть `id=1`, а пустая active SQLite по умолчанию выдаёт новому outcome `id=1`.
  Сейчас пересечения между частями нет. Демонстрация выполнена в `:memory:`.
- [ ] Разработать и проверить сохранение глобального порядка и идентичности outcome

  поэтому одного `UNION ALL` или независимых генераторов ID недостаточно.
- [ ] Реализовать и проверить полный composite reader всех существующих API и
