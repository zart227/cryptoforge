# Supabase Persistent Backend

CryptoForge uses Supabase for durable state that is valuable after a
process restart or VPS replacement. It is not part of the critical path
for managing an already-open position; the trading runtime must continue
to make safe local decisions if Supabase is offline.

## Schema

The initial schema is stored in
`supabase/migrations/20260925000100_initial_schema.sql`.
Server-side Data API grants for the secret/service role are stored in
`supabase/migrations/20260925000200_grant_service_role_server_access.sql`.

Core tables:

- `strategies`: logical strategy families and lifecycle status.
- `strategy_versions`: immutable-ish strategy revisions, parameter sets,
  source hashes and risk profile metadata.
- `trades`: compact trade journal for Bybit Spot dry-run and future
  audited live trades, including the market regime known at entry time.
- `trade_features`: bounded feature snapshots around trades.
- `experiments`: research, backtest, model and parameter-search metadata.
- `backtest_runs`: summarized backtest runs.
- `walk_forward_runs`: summarized walk-forward validation runs.
- `model_runs`: model training metadata and object-storage artifact
  references.
- `model_metrics`: normalized model metrics for comparison.
- `daily_metrics`: daily portfolio and strategy summaries.
- `system_events`: operational audit events delivered through the future
  local outbox.

All primary keys are UUIDs generated by PostgreSQL. Tables use
`created_at` consistently, and mutable entities also use `updated_at`
maintained by an internal trigger function.

## Security

The backend is server-side only at this phase. The service-role key must
stay in server or VPS environment variables and must never be exposed to a
browser, committed to Git, or printed to logs.

The migration enables row-level security on every public table and
revokes table access from the `anon` and `authenticated` roles. No
frontend policies are created yet because there is no frontend data
access requirement. If a dashboard is added later, it should receive
least-privilege read policies or a separate backend API rather than broad
table access.

The server-side secret key uses the privileged `service_role` context.
That role receives explicit table privileges so backend delivery through
the Supabase Data API works while RLS remains enabled and client roles
remain closed.

## Storage Policy

PostgreSQL stores metadata, checksums and summaries. It does not store
model binaries as `BYTEA`, and it does not store unlimited raw candles,
ticks or order-book data.

Future Supabase Storage convention for important model artifacts:

```text
models/{strategy_id}/{model_run_id}/{artifact_sha256}-{filename}
```

Required artifact metadata:

- `artifact_uri`: storage URI or external durable object reference.
- `artifact_sha256`: checksum of the stored artifact.
- `model_family`, `feature_version` and train/validation/test ranges.
- Metrics sufficient to decide whether the artifact can advance through
  validation gates.

Raw Bybit market data is normally reproducible and should remain local,
cached or re-downloadable unless a later phase documents a bounded reason
to persist a curated subset.

## Current Verification Status

The migration is authored in Git, but it has not been applied to a
Supabase project in this environment because Supabase credentials and CLI
configuration are not present. Local SQL/file checks cover the expected
tables, RLS posture and storage exclusions until a real project is
connected.
