# Причина потери контекста десяти выходов

**Обновление:** пять исходных решений найдены в executor stdout и добавлены
в базу с проверкой чтением. Актуальное покрытие **25/30**, для PONS
stop_loss=True подтверждён исходным логом. Ниже сохранён предыдущий этап
расследования; его утверждение об отсутствии всех десяти причин устарело.
См. [восстановление и подключённую защиту](EXIT_CONTEXT_RECOVERY_AND_DURABILITY_20261102.md).

Продолжение сверки 2 ноября 2026. Предыдущий вывод «контекст отсутствует»
уточнён: для всех десяти выходов обнаружена коллизия старого ключа решения.

## Короткое объяснение для продолжения другим агентом

Отсутствуют не сделки, а первоначальные значения `reasons` и `features.order`
в десяти строках `trade_decisions`. Продажи подтверждены Bybit. Исторический
код делал UPDATE существующей строки при совпадении ключа пары и свечи,
поэтому следующий цикл заменял её содержимое. SELECT текущей таблицы не
возвращает предыдущую версию строки. Повторный запрос исполнений к Bybit
тоже не возвращает внутренние RSI, exit_trend_down или stop_loss бота.

Пример PONS: продажа orderId 2320770872308492800 исполнена
7 октября в 17:17:26.899 UTC. Соответствующая строка создана в
17:17:27.128555 UTC, но теперь её decided_at — 17:22:29.625898 UTC,
decision — hold, reasons содержат ignored_dust=0.07408, orderId отсутствует.
Хеш orderLinkId продажи указывает на ту же свечу, что и старый ключ строки.
Это более позднее наблюдение остатка после продажи, а не объяснение продажи.

Дамп 20 октября содержит уже заменённые строки, поэтому восстановление
этого дампа не вернёт исходные причины. Для дальнейшего восстановления
нужен новый независимый источник: более ранний снимок между продажей и
перезаписью, ранее настроенный аудит/CDC, доступная цепочка PITR/WAL за тот
момент либо журнал исходного процесса с полным решением. Наличие этих
источников не установлено; глобальная невозможность восстановления не
доказана. Проверены только перечисленные в этом отчёте доступные источники.

Расчёт сигналов на сегодняшних исторических свечах может дать реконструкцию,
но не докажет исходное решение без точного кода, настроек и входного снимка
на момент отправки: бот мог видеть ещё формирующуюся свечу. Не повышать
coverage 20/30 за счёт соседних hold/reject_entry или предположений о стопе.
Следующий полезный шаг — искать независимый архив на исходном хосте или
у провайдера базы, а не повторять те же SELECT и пересчёт FIFO.

## Установленный механизм

В старой версии `_record` сохранял любое решение через merge-upsert по
`order_id(pair, latest.open_time)`. Ключ не включал ни тип решения, ни
биржевой orderId. Следующий цикл на той же свече мог заменить approve_exit
решением hold или reject_entry и очистить features.order вместе с причинами.
Исторический исходник: `git show f448348:src/cryptoforge/supabase_executor.py`.
Legacy-формат cf-<28 hex> проверен по исходнику commit 932a2e9; формат
cf-<instance>-<20 hex> — по order_observer.instance_order_id.

Для каждого из десяти ордеров заново прочитаны полная карточка Bybit по
orderId и решения базы в окне ±10 минут, без фильтра decision/mode.
Сопоставление использует не близость времени: SHA-256 от
`pair + ':exit:' + latest_open_time` должен точно дать orderLinkId продажи;
SHA-256 от `pair + ':' + latest_open_time` должен точно дать сохранённый
ключ строки решения того же экземпляра. В ней нет orderId, а decided_at
позже исполнения. Это воспроизводимо для **10 из 10**.

В восьми случаях created_at строки находится через 0.183–0.321 секунды
после исполнения, но decided_at и содержимое уже относятся к следующему
циклу. Для 0G и старого NEAR строка создана раньше исполнения: это
согласуется с несколькими обновлениями одной свечи. Здесь нет отдельной
сохранённой версии строки, доказывающей её промежуточное содержимое.
Таким образом, механизм и совпавшие ключи установлены, исходные значения
RSI/stop_loss каждого утраченного approve_exit не восстановлены.

## Архив и проверка исправления

Из `.local/database/backups/cryptoforge-20261020T110545Z.dump` только на чтение
извлечена trade_decisions подходящим pg_restore 17. База не восстанавливалась
и не изменялась. Все десять соответствующих строк в архиве уже содержат
те же перезаписанные решения; ни один из десяти orderId не найден в
features архивной таблицы. Значит, этот доступный backup не возвращает
исходные причины. Локальные system/user journald записи executor за даты
выходов отсутствуют. В доступных JSON-снимках точные approve_exit этих
десяти ордеров не найдены.

Текущая версия executor уже использует ключ конкретного биржевого ордера
и ignore-duplicates. Добавлен regression test: approve_exit первого ордера
сохраняется после hold, reject_entry, второго выхода и повтора первого
ордера с другим контекстом на той же свече. Исходная причина не меняется.
Торговые правила, runtime и база не изменялись.

Доказательства: `.local/state/missing-order-context-20261102/` — десять
orderId.json с ответами, diagnosis.json с хешами исходных файлов и runtime
кода, backup-decisions.json с SHA дампа и backup-verification.json.
Повтор анализа: `scripts/diagnose_legacy_exit_context.py --evidence-dir DIR
--output NEW_REPORT`. Анализатор отвергает чужой orderId/ключ, другую свечу,
контекст с уже сохранённым orderId и записи до исполнения. Пакет тестов
анализатора, executor и feedback: **35 passed**.
